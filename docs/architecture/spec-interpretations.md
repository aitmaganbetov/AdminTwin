# Интерпретации ТЗ v1.3.1, принятые на Этапе 0

Документ фиксирует места, где ТЗ допускает несколько прочтений, и выбранный вариант.
Каждый пункт можно пересмотреть; при изменении — обновить код, тесты и этот файл.

## I-01. Режимы Observer / Advisor: исполнение невозможно даже с согласованием

Матрица §11.4 для Observer/Advisor содержит только «предложение», а инвариант продукта гласит:
«В режиме по умолчанию (Advisor) действия только предлагаются». Принято: в этих режимах ChangeRequest
переходит в состояние `proposed`, согласование отклоняется с `403 policy-denied`. Чтобы исполнить, Tenant
Admin переводит tenant в Operator. В Observer недоступны даже предложения рисков выше `low` (в матрице «—»).

## I-02. Дополнительные состояния ChangeRequest

Базовый автомат §11.1 / C.8 расширен состояниями, которые следуют из текста ТЗ, но не названы явно:

| Состояние | Откуда в ТЗ |
|---|---|
| `waiting_approval` | §13: «`202` + `status: waiting_approval`» |
| `proposed` | §11.4: режимы Observer/Advisor — только предложение |
| `preflight_failed` | §11.1: «preflight выполняется перед `executing` независимо от решения» |
| `compensated` → `closed_with_compensation` | C.0: «closed \| rolled_back/compensated → PIR» |
| `failed` | исполнение не началось (Vault недоступен, движок отсутствует) — §17.2 |

Отклонённый политикой запрос **сохраняется** со статусом `rejected` (для аудита), а ответ API содержит
`change_id` — как в примере problem-ответа §13.

## I-03. Завершение операции во время отмены

Если kill switch / отмена пришли, когда движок уже завершил действие, результат — `unknown → manual_review`,
а не `verified`: §11.7 запрещает утверждать исход без подтверждения, а автомат C.8 из
`cancellation_pending` допускает только `cancelled | unknown`.

## I-04. Legal hold проверяется дважды

Policy Engine отклоняет создание change для актива под legal hold (`409 legal-hold`, §13), а preflight
`legal_hold_absent` повторяет проверку непосредственно перед исполнением (защита от TOCTOU). Проверка
обязательна для **всех** runbook (C.0 «Общие preflight-проверки для всех write-операций»), а не только для очисток.

## I-05. Dry-run

Dry-run включается либо флагом ChangeRequest `dry_run`, либо параметром runbook `dry_run: true`.
Если runbook не поддерживает dry-run (`supports_dry_run: false`), запрос завершается отказом без исполнения —
пробный прогон никогда не подменяется настоящим.

## I-06. Rate limit runbook считается по исполнениям

`rate_limit` (§11.3) ограничивает число начатых исполнений runbook по активу (или tenant) в окне;
исполнения, остановленные на preflight, не учитываются. Превышение — `403 policy-denied`.
Отдельно preflight `restart_count_last_hour_lt` проверяет фактические перезапуски объекта по данным коннектора.

## I-07. Подстановка параметров в argv

«Строковая интерполяция в shell запрещена» (§11.2 п.7) реализована строго: плейсхолдер `{{param}}` может
занимать только **целый** элемент argv; частичная подстановка (`--name={{x}}`) и shell-метасимволы в
статичных элементах запрещены валидатором каталога. Строковые параметры обязаны иметь якорный `pattern`
(`^...$`) или `enum`.

## I-08. Engineer согласует только в своей области

Тип актива → scope Engineer: `docker_host`/`kubernetes_cluster` → devops, `linux_host`/`windows_host` →
sysadmin, сетевые → network, `database` → dba. Для `high`/`critical` Engineer не согласует вовсе (§2.2).

## I-09. Машинная идентичность не несёт человеческих ролей

Если запрос от `ai_agent` содержит человеческие роли, они отбрасываются (защита от confused deputy, §18.6).

## I-10. Один бинарник ядра на Этапе 0

Сервисы §3.4 реализованы как отдельные Go-пакеты в `services/*`, собираемые в один бинарник
`admintwin-core` (§3.5: «один бинарник для on-prem»). Разделение на процессы — при переходе на NATS (этап 2).
